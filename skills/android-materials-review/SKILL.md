# Android教材のPRレビュー

学生が指定環境の開始コードに教材の手順を順番に適用して、課題の完成条件まで到達できるかを確認する。完成コードが正しいだけでは合格としない。

このファイルは特定のAI製品、レビューサービス、MCP、GitHub CLIに依存しない。利用するエージェントにこのファイルを読ませ、PRの対象差分を渡して使う。パスはリポジトリルート基準で記す。以下のリンクはこのファイルからの相対パス。

## レビューの基準を確認する

- [docs/course-plan.md](../../docs/course-plan.md)：指定Android Studioの**バージョンの正本**、対象学生、学習範囲、実装制約、例外。スキル内にバージョンを固定しない。
- [docs/teaching-materials-guide.md](../../docs/teaching-materials-guide.md)：学生向け文章、変更前後の示し方、macOSの操作、配布前の検証基準。
- 対象の `assignments/<課題>/README.md`：課題固有の仕様、開始条件、完成条件。`materials/plan.md` など：検証した環境・操作・結果と未実施事項。
- 変更対象のHTML、配布コード、テンプレートの取得記録・比較用ファイル・差分。A01では [template-baseline.md](../../assignments/A01-first-app/materials/template-baseline.md) を入口にする。他の課題にA01固有の設定を強制しない。

レビュー対象のベースと変更後のリビジョンを特定する。PRで変更された箇所を中心に、前後の手順と参照先も読む。仕様間の矛盾は推測で片方を正しいと扱わず、学生の作業に与える影響を示す。明示された課題の例外や今回のユーザー指示を考慮する。

## 必須観点：テンプレートから変更をたどれるか

### 1. 開始コードの根拠

- 授業計画の指定バージョンで **Empty Views Activity・Java** を選んだ生成物を起点としているか確認する。Compose用のEmpty Activity、別バージョンの生成物、完成コードから逆算した例を同じ根拠と扱わない。
- 取得記録と実際のファイルを照合する。IDEのバージョン・ビルド番号、テンプレート、言語、プロジェクト名、パッケージ名、Minimum SDKなど、生成内容に影響する条件を確認する。必要に応じてAGP・Gradle・SDK・初期依存関係も比較する。
- 同じIDEでも入力条件によって生成内容が変わり得る。特に別のminSdkで生成してから数値だけ変更したビルド結果は、教材と同じ設定で新規生成した証拠ではない。テンプレートの条件分岐を調べるか、同じ設定の生成物と比較する。確認できなければ、その範囲を未検証とする。
- 名前・パッケージ・改行などを読み替えた比較用コードは、取得原本と区別され、読み替え内容を追えるか確認する。記憶や一般的なテンプレート例だけで「生成直後と一致」と判定しない。
- 後続課題が検証済みの開始用プロジェクトを配布する場合は、そのリビジョンと授業用の変更内容を起点にする。学生が毎回新規作成する条件へ勝手に変更しない。指定テンプレートから配布状態までの教員側の変更履歴も確認する。

### 2. 手順ごとの編集場所と変更前後

各編集手順を、直前の手順を終えた状態に適用して確認する。

- 開くファイルの場所が一意にわかるか。同名ファイルがある場合は `res/values/themes.xml` と `res/values-night/themes.xml` のように区別できるか。
- 追加・変更・削除の種類と範囲、探す文字や前後の行が示されているか。変更前のコードはその時点のファイルに存在するか。
- 変更前と変更後が学生向けHTMLに載っているか。教員向けの差分ファイルや変更後の全文へのリンクだけで説明を済ませていないか。
- 初期コードから必要な箇所を直す手順になっているか。全文置き換えだけで済ませ、何を残して何を変えたか隠していないか。短いファイル全体の比較を使う場合も変更箇所がわかるか。
- 表示例をコピーすると、行番号、差分の `+` / `-`、省略記号、HTMLの装飾がコードに混入しないか。部分例をファイル全体として貼る誤解を招かないか。
- 変更しない重要なコードやファイルが明示され、後の説明・配布コードも同じ状態になっているか。課題中に文字などを変える場合は、変更後の全文やダウンロードコードが**どの手順の状態か**明確か。

### 3. テンプレートの処理と変更内容の整合

生成コードに実在する依存関係を追う。例えば、Javaが参照するXMLのID、Activityとテーマの継承関係、Manifestの登録、システムバーの余白処理は、関連ファイルの片方だけを変えると不具合になり得る。

- レイアウト変更でIDを消し、既存の参照先を失っていないか。既存の余白処理を残す場合、教材で加える余白との役割が整理されているか。
- Activityやテーマを変更するなら、初期コードとの違い・必要な理由・関連する修正が手順に含まれているか。特定の継承クラスを一律に正解とせず、課題仕様と生成コードに基づいて判断する。
- 新しい依存関係やGradle・SDK設定の変更を、説明のない事前準備として要求していないか。初期依存に含まれるライブラリと追加導入を区別する。
- 課題の完成コードがJava・XML・レイアウト・テーマ・処理配置などの方針に従うか。**比較用の生成原本にConstraintLayoutやDayNightがあるだけでは違反としない。** 授業用状態へ直す手順と最終結果を見る。

## 学生が読み進められるか

教材作成方針と照らし、変更箇所について次を確認する。

- 初学者が操作する場所を特定でき、短い日本語で1つずつ操作し、期待する結果を確かめられる。新しい専門用語に説明がある。
- 学生のOS・IDEに合うラベルとキー表記である。自動保存の編集に手動保存を繰り返し要求しない。すでに表示されるProjectを開く説明などは、必要に応じて復帰手順へ分ける。
- 完成条件、必須課題、追加練習、提出物が一致する。追加練習をしない学生も次の必須手順へ進める。
- HTMLの目次・手順リンク・画像・コードのダウンロードが使える。本文の読み取りに外部CDNやJavaScriptを必須としていない。画面の拡大やキーボード操作で重要な説明を失わない。
- Stitch参照画像・説明図・実行画像の区別がつき、確認していない完成画面を実行済みの証拠として示していない。

## 検証と判定

可能な範囲で、指定開始コードの一時コピーに手順を順番に適用する。元の取得物や学生のプロジェクトを上書きしない。ファイル間の参照、コード例と配布ファイル、HTMLリンクを確認し、変更に見合うビルド・実行確認を行う。

検証結果は次を区別する。XML/Java単体のコンパイル成功や別環境のビルド成功を、全項目の確認済みへ拡大しない。

| 確認対象 | 記録する根拠 |
| --- | --- |
| テンプレート一致 | 取得条件、生成物、比較・読み替え内容 |
| 手順の適用 | 開始リビジョン、適用した手順、相違や不足 |
| ビルド | 対象コード、使用環境、コマンドまたはIDE操作、結果 |
| 実行・完成条件 | 端末/API、実際に確認した操作・表示、結果 |
| 教材表示・操作 | 対象HTML、確認したリンク・表示・操作、結果 |

環境や証拠が足りない項目は「未検証」とし、不具合が再現した場合と分ける。未検証でも教員確認用原稿として適切に表示されているなら、自動的にマージ禁止とはしない。配布可能と宣言する変更では、未検証の必須手順を重要な残件として扱う。

## レビュー結果の伝え方

指摘ごとに、対象ファイル・行または手順、根拠、学生が困る具体的な操作、影響、最小限の修正案を示す。対応の必要性は次で判断する。

- **対応が必要**：手順を適用できない、ビルド・実行が壊れる、必須仕様に反する、未確認を確認済みと表示するなど。根拠と再現条件を示す。
- **任意対応**：完了はできるが読みやすさを改善できるなど。効果と修正コストを示し、重大な不具合と混ぜない。
- **対応不要**：根拠がない、誤認、明示された例外、別の場所にすでに有効な説明があるなど。確認した参照先と理由を示す。

確認済み事項、未検証事項、残る指摘を分け、マージ可否と学生への配布可否を別々に述べる。このスキルの使用だけでコメント投稿・修正・コミット・マージの権限を得たと解釈しない。外部投稿や修正は依頼範囲に従い、既存スレッドを扱う場合は新しい情報のない重複返信を避ける。
