# 学生向けHTML教材の作成方針

## 1. 対象と基本方針

プログラミングとAndroidアプリ開発を初めて学ぶ学生を対象とする。ほとんどが留学生であるため、難しい言葉はできるだけ使わず、短い日本語と画面例で説明する。「コードを書いたことがある」「ファイルの場所がわかる」ことを前提にしない。

学生全員がmacOSを使用する。操作説明・キー表記・ファイル管理の案内はmacOSに統一する。

学生向けの説明・課題・動作確認票はHTMLファイルで作成する。教員向けの授業計画・仕様・設計上の判断はMarkdownで管理する。

教材の基本の流れは、**完成例を見る→1つ操作する→結果を確かめる→少し変えてみる**とする。写して終わりにせず、自分で変えた結果を確認する場面を必ず用意する。

## 2. 教員側の準備と学生側の学習

| 対象 | 行うこと | 成果物 |
| --- | --- | --- |
| 教員 | Stitch MCPで画面のデザイン情報・画像・生成コードを取得し、授業仕様に沿ってJava・XMLへ反映する。 | 検証済みのAndroidアプリ、取得原本、仕様との差分記録。 |
| 教員 | 指定Android Studioで手順を実行し、画面と操作名を確認する。 | 実行画面の画像、各手順の説明、つまずいた場合の確認方法。 |
| 学生 | HTML教材を読み、自分のAndroid Studioで操作・入力・実行・確認する。 | 提出はAPKファイル1つのみ。完成条件の確認・実演・短い振り返りは授業内で行う。 |

学生にStitchやMCPの設定・操作は要求しない。Stitchの生成HTMLは画面デザインの参考資料、学生配布用HTMLは授業を進めるための教材として管理する。

各課題の提出物はAPKファイル1つのみとする。Android StudioのAPK生成操作、生成先、ファイルの取り出し方、提出前の確認を1つずつ説明する。授業では初期設定のdebug APKを使い、署名鍵の作成・管理は学生に要求しない。プロジェクト一式・ZIP・ソースコード・画像・振り返り文を提出物へ追加しない。教員から学生へ配布する開始用プロジェクトのZIPは、提出物とは区別する。

Stitchから取得したコードやデザイン定義は、採用済みのJava・XML・LinearLayout・ライブラリ制限と、テンプレートのテーマ設定を維持する方針に合わせて扱う。生成物に含まれる追加動作や部品を、学生の必須課題へ自動追加しない。

## 3. 文章のルール

1. **1つの文に1つの操作を書く。** 「開いて変更して実行する」は、3つの手順に分ける。
2. **場所と操作を具体的に書く。** ファイル名、ボタン名、変更する文字を示す。「適切に設定する」「同様に行う」で済ませない。
3. **先に意味を説明し、必要な名前を後から紹介する。** 例：「画面に文字を置きます。この部品の名前はTextViewです。」
4. **API名・ファイル名・画面上のラベルは正確に示す。** やさしい説明を添え、学習に必要な正式名称を隠さない。英語のボタンは画面と同じ表記にし、日本語の意味を添える。
5. **短い段落に分ける。** 長い注意書きや複数の条件を、1段落に詰め込まない。
6. **「簡単」「当然」「前にやったので省略」を使わない。** 再登場する操作にも短い案内か戻り先のリンクを付ける。
7. **指示語だけで説明しない。** 「これ」「そこ」「右のもの」ではなく、対象の名前と画像内の番号を示す。
8. **入力する内容を区別する。** 日本語の文章を変える箇所と、記号・英数字をそのまま入力する箇所を明示する。全角・半角が関係する場所には例を添える。
9. **新しい用語を一度に増やさない。** その手順で必要な用語だけを説明し、詳しい仕組みは補足へ分ける。読み方が難しい語には必要に応じてふりがなを付ける。
10. **日本語の上手さと、操作・処理の理解を分ける。** 確認問題は、選択・指差し・結果の予想・短い説明でも答えられる形にする。

### 言い換えの例

| 教材で避ける説明 | 学生向けの説明例 |
| --- | --- |
| プロジェクトを生成します。 | アプリを作るためのファイル一式を用意します。このまとまりを「プロジェクト」と呼びます。 |
| TextViewを配置します。 | 画面に文字を置きます。文字を表示する部品の名前は「TextView」です。 |
| リソースを変更します。 | strings.xmlを開き、表示する言葉を書き換えます。 |
| ビルドして起動します。 | 書いたコードから、動かせるアプリを作ります。これを「ビルド」と呼びます。作ったアプリを起動して、画面を見ます。 |
| エミュレーターで検証します。 | パソコンの中で動く練習用のスマートフォンで、アプリを確かめます。これを「エミュレーター」と呼びます。 |
| 値を永続化します。 | アプリを閉じても残るように、値を保存します。 |
| バリデーションを実装します。 | 入力が空でないか、使える数になっているかを確かめます。 |

言い換えだけでは手順にしない。実際の教材では、これに操作する場所・番号付きの手順・期待する結果を組み合わせる。

## 4. 1課題の教材構成

| 順番 | 学生向けの見出し | 入れる内容 |
| --- | --- | --- |
| 1 | 今回つくるもの | 完成したアプリの画像、何ができるか、今回の目標を短く示す。 |
| 2 | はじめる前に | 必要な環境、使うファイル、前の課題でできていることを確認する。 |
| 3 | まず動かしてみよう | 最初の小さな成功を作る。準備だけで1課題を終えない。 |
| 4 | 1つずつ作ろう | 番号付きの短い手順で作り、区切りごとに結果を見る。 |
| 5 | 自分で少し変えてみよう | 学習済みの範囲で値や文言を変え、変化を予想して実行する。 |
| 6 | できたか確かめよう | 完成条件を、学生が操作して確認できるチェック項目にする。 |
| 7 | 提出しよう | 提出物、名前、提出先、提出前の確認を明示する。 |
| 8 | 今日の振り返り | 今日できたことと、まだ難しいことを短く答える。 |

追加の練習は必須課題の後に置き、必須部分と見分けられる見出しを付ける。後続の必須課題が、追加練習を終えた前提にならないようにする。

### 各手順に必ず入れる情報

- **この手順でやること**：目的を1文で示す。
- **操作する場所**：アプリ名・ファイル名・画面上の場所を示す。
- **やってみよう**：1項目1操作の番号付き手順にする。
- **こうなればOK**：表示文字や画面例など、見て判断できる結果を示す。
- **うまくいかないとき**：よくある症状、最初に見る場所、直し方か教員に見せる情報を示す。

所要時間は目安として示し、早さを評価しない。90分の授業中に、実装・確認・修正・質問の時間を含める。

## 5. コードと画像の見せ方

- コードの前に「開くファイル」「追加／置き換えのどちらか」「変更する範囲」を示す。
- 初登場の短いXMLは、貼り付け位置がわかる全体例を用意する。長いコードは段階に分け、どこに入るかを前後の行で示す。
- 「...」を含む省略例を、そのまま貼り付けるコードとして表示しない。行番号や説明文がコピー内容に混ざらないようにする。
- 変更前と変更後を示す。色だけに頼らず、「ここを書き換えます」と文章でも説明する。
- 指定バージョンのEmpty Views Activityが生成するJava・XMLを開始状態として確認・保存し、教材に対象ファイル・変更箇所・変更前後を示す。変更しないファイルや既存処理も明示する。
- テーマは生成時の設定をそのまま使う。学生にテーマファイルの編集や端末の表示モード切り替えを求めず、通常の端末設定で学習できる手順にする。テーマごとの見た目を課題の採点条件にしない。
- 全文の置き換えだけを通常手順にせず、初期コードから必要な箇所を直す。変更後の全文は確認用に添える。その後に、学生自身が1か所を変更して結果を確かめる。
- スクリーンショットは指定のAndroid Studio Panda 2 | 2025.3.2と、検証済みのアプリから取得する。画面に出ていないボタンや設定を推測で手順に書かない。
- 画像には説明と代替テキストを付ける。操作対象を番号や枠で示し、画像の文字だけに指示を置かない。
- 操作説明はmacOS向けとし、コピー・貼り付けは⌘キー、ファイル管理はFinderを使う。
- Android Studioの自動保存を前提とし、編集後はそのまま実行へ進む。手動保存を繰り返す手順は設けない。提出用APKの取り出し、開始用ZIPの展開、アプリ内のデータ保存は必要な場面で別に説明する。
- 初期状態ですでに表示されているProjectを開く操作や、表示方法を切り替える操作は通常手順に含めない。一覧が見えない場合などの復帰方法は「うまくいかないとき」へ分ける。
- Stitchの参照画像と、実装済みアプリの実行画像を区別する。仕様と異なる生成画像を、完成条件を満たした実行画像として使わない。

## 6. HTMLファイルの構成

課題ごとに次の構成を基本とする。A01では[HTML教材の初版](../assignments/A01-first-app/materials/lesson.html)を作成済み。配布前の検証状況は各課題のplan.mdで管理する。

```text
materials/
  index.html         学生向け：教材の入口・Classroomからの開き方
  plan.md            教員向け：章立て・画面取得・検証の準備
  lesson.html        学生向け：目標・準備・操作手順・困ったとき
  exercise.html      学生向け：必須課題・追加の練習
  checklist.html     学生向け：完成確認・提出・振り返り
  assets/            画像・CSSなど
```

HTMLはUTF-8・日本語指定で作成し、ブラウザーで直接開ける構成を基本とする。目次、現在の手順番号、前後の手順へのリンクを用意する。本文は18px程度・十分な行間を基準とし、拡大しても読めるようにする。コードの長い行はコード欄内でスクロールできるようにする。

本文、画像、CSSは教材フォルダ内にそろえ、通常の閲覧にログインや外部CDNを必要としない。外部の参考リンクは補足として扱う。JavaScriptを使う場合も、基本の説明と操作手順はJavaScriptなしで読めるようにする。コピー機能や進捗表示は補助とし、それが使えなくても授業を進められるようにする。

Google Classroomでは、学生向けHTMLと参照ファイルを課題ごとのZIPとして共有する。学生はMacへダウンロードし、展開したフォルダーのindex.htmlを開く。HTMLの個別添付、Driveプレビュー、教員のlocalhostへのリンクを閲覧の前提にしない。比較用コードの全文は可能ならページ内で展開して読める形にし、別ファイルの取得だけに依存しない。[Classroomへの添付方法・版の更新・学生向け案内](classroom-distribution.md)を参照する。

授業開始後のFBはGoogleフォームで受け付け、[教材更新の手順](materials-maintenance.md)に沿って管理する。修正の開始時と終了時に残件を確認し、FBの対応版、検証、学生向け更新案内、全配布先への掲載確認を記録する。同じ版のZIPを別の内容で上書きせず、コード修正だけで配布完了にしない。

教材HTMLの読みやすさは、開発対象アプリの「スマートフォンのみ」という制約とは別に扱う。学生のPCで教材とAndroid Studioを並べられるようにし、キーボード操作、拡大表示、印刷時の読みやすさも確認する。

## 7. 配布前の確認

- 指定環境の開始状態から、書かれた順に操作して完成できる。
- 初めて出てくる用語、ファイルの開き方、待つ場面の説明がある。
- 各手順に期待する結果と、つまずいた場合の案内がある。
- コード例と完成例の内容が一致し、追加ライブラリなど未記載の準備がない。
- 初学者役の確認者が手順を読み、説明不足の場所を記録して修正する。
- HTMLの目次・手順リンク・画像が表示され、配布フォルダを別の場所に置いても開ける。
- 実際の配布ZIPを別の場所へ展開して参照を検査し、学生用アカウントで取得・展開・index.htmlの直接表示を確認する。教員用の完成解答・制作記録が混ざっていないか確認する。
- 完成条件・提出先・提出形式が決まり、教員用の未確定事項が学生向け本文に残っていない。
- 提出物がAPKファイル1つのみであり、取り出したAPKを授業用端末へインストールして完成条件を確認できる。

確認者・確認日・対象コードのコミット・使用環境を教員用のplan.mdに記録する。未検証の手順は教員用原稿で扱い、配布可能と表示しない。

## 8. 参考資料と参考にする範囲

- [Google Codelab：Create your first Android app](https://developer.android.com/codelabs/basic-android-kotlin-compose-first-app)は、事前準備、学習目標、完成例、番号付き操作、画面例を示す構成の参考にする。この資料自体はKotlin・Composeを使用するため、Java・XMLの操作手順や環境設定をそのまま転用しない。
- [Google Codelabs Formatting Guide](https://github.com/googlecodelabs/tools/blob/main/FORMAT-GUIDE.md)は、手順の区切り、所要時間、補足・注意、コードの示し方の参考にする。

上記は構成を検討する教員向けの参考資料であり、学生が事前に読んで理解することは必須にしない。教材の日本語、課題、画像は本授業向けに作成する。Codelab用の生成ツールの導入は、今回のHTML配布方針の必須条件ではない。
